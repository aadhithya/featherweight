    Attachments¶

    Status: implemented, in epic #170: the converters and what ChatInput refuses (#171), the limits (#172), the provider tests (#173), the adapters (#174), and the guide (#175). It changes streaming agents (ChatInput, to_langchain, to_agui, the Vercel adapter), and nothing else.

    Goal¶

    A person in a chat attaches an image, a PDF, a recording or a video to a message, and the model reads it. A user message of a ChatInput carries them next to its text (streaming).

    featherweight is the transport. It takes what the client sent and hands it to the LangChain model underneath, in LangChain's provider-independent content blocks. It does not check what the model can read, it does not download, upload, convert, resize or store anything. Whether an attachment suits the model is the application's responsibility, and the provider says so when it does not. The application decides how files reach it: uploads, a store, fetching, scanning.

    What a client can send¶

    AG-UI 1.0 messages from a user can hold text, image, audio, video and document parts. Each media part has a source:

    Source Meaning Here
    data the bytes, base64-encoded, with a required mime_type accepted
    url a URL, "fetched by whoever needs them" refused

    A url source is refused because nothing in featherweight should fetch a URL that a client chose, and because what happens to one depends on the provider: langchain-google-genai downloads an http(s) URL in the server process, langchain-anthropic and langchain-openai pass it to the provider. An application that wants URLs fetches them itself, checks them as it sees fit, and sends the bytes as a data source. We offer no hook for that: how to fetch safely is the application's decision.

    The legacy binary part of AG-UI 0.x is retired in 1.0 and is not supported.

    What data is. Standard base64 (the alphabet of RFC 4648, section 4), padded, in one line, with no data: prefix: what Python's base64.b64encode and JavaScript's btoa give, and nothing else. It is checked when the ChatInput is built, so a wrong one is raised before a run exists. These are refused, and the error names the likely cause (it never quotes the data):

    What was sent Why it is refused The way out
    a data:image/png;base64,... URL (what a browser's FileReader.readAsDataURL gives) it is a URL, not base64 send only the part after the comma
    line breaks or spaces (Python's base64.encodebytes wraps every 76 characters) not one line send it in one line
    - or _ the URL-safe alphabet send the standard alphabet (+ and /)
    a length that is not a multiple of 4 no padding pad it with =
    any other character, or = before the end not the base64 alphabet, or padding in the middle the error says which of the two
    an empty value an empty attachment is refused: there is nothing to send, and the provider would say no after a run exists send a file with bytes in it, or no attachment

    The check decodes the value in chunks of 64 KB and drops each one, so the memory it needs does not grow with the size of the attachment. The limits of the agent (below) are checked later, from the length of the text, without decoding.

    What the model is given¶

    to_langchain turns each part into a LangChain standard content block, and the provider's package turns that into its own request:

    AG-UI part LangChain block
    image {"type": "image", "base64": ..., "mime_type": ...}
    document {"type": "file", "base64": ..., "mime_type": ..., "filename": ...}
    audio {"type": "audio", "base64": ..., "mime_type": ...}
    video {"type": "video", "base64": ..., "mime_type": ...}
    • filename comes from the part's metadata["filename"] when there is one. OpenAI wants a name for an inline file, and LangChain otherwise puts in a placeholder and warns. We never invent one.
    • Parts of a message keep their order, and the text parts around them.
    • to_agui is the inverse, so a stored conversation with an attachment survives from_langchain and back.
    • An assistant, tool or system message carries no attachments; they stay text.
    • Provider-side files (an uploaded file's file_id) cannot be said in AG-UI. An application that uses them builds its own LangChain message with a {"type": "file", "file_id": ...} block. Nothing here blocks that, and nothing here helps with it.

    Limits¶

    Every turn sends the whole conversation, so an attachment in an earlier message is sent again and counts again. The limits apply to all the attachments of the conversation, not to the last message.

    Limit Default Counts
    max_attachments 10 the media parts of all messages
    max_bytes 15 MiB (15,728,640 bytes) the decoded size of all of them

    The application sets them on the agent, with a class attribute, and the runner checks them when a turn starts. A limit is a whole number of 0 or more. max_attachments = 0 turns attachments off for that agent: any attachment is refused, and a message with only text passes. A conversation over either limit raises AttachmentLimitError before any run exists.

    Where the defaults come from. The size is a cautious value that Anthropic, Google and OpenAI all accept; the count is our own choice. The providers' figures are in what the providers accept (read it with its warning: it is a dated snapshot, and the providers' pages are the source):

    Provider Count per request Size of a request
    Anthropic 100 images (600 for some models) 128 MB
    Google no count stated for documents; 3,600 images (unconfirmed) 100 MB inline, 50 MB for PDFs; one page still says 20 MB
    OpenAI 1,500 images; none stated for files 512 MB of images; 50 MB for all files together

    The default count is 10, a design choice, not a provider's limit: every provider accepts more (the lowest is Anthropic's 100 images), but a chat that takes 100 files in one go is a different job: a pipeline that keeps the files in a store and passes references (below). 10 is also what the Gemini app allows. An application that needs more raises max_attachments. For size the pages disagree: the lowest figure on any of them is Google's 20 MB, the next is OpenAI's 50 MB for files. Base64 makes data a third larger, so 15 MiB of decoded bytes is exactly 20 MiB on the wire: that lowest figure and no more (and over it, if "20 MB" is read as 20 million bytes). It is under every other figure. The default is the cautious one: Google has since raised its inline limit to 100 MB, and an application that has checked its provider raises it. Anthropic also applies a stricter pixel limit past 20 images or documents: that is the provider's to report. These are ceilings against a request that cannot work, not a promise that every request under them does: a provider also limits pages, pixels and the type of each file, and says so in its error.

    Failures¶

    Consistent with the rest of featherweight: a thing that is wrong with the input is raised; a thing that goes wrong in the run is a result.

    • Raised, before any run exists: a url source; a part type that is not supported; data that is not base64; an empty attachment; a missing mime type; more attachments or bytes than the agent allows. Nothing is started, and nothing is written to the run log.
    • The limits raise AttachmentLimitError, a subclass of BadRequest (so a ValueError, and a handler for BadRequest answers it too), from runner.stream(). The input cannot refuse it earlier: the adapters build a ChatInput before they know the agent and its limits. A web application answers it as a request that cannot be taken: 413 for AttachmentLimitError (a handler for the subclass wins over the one for BadRequest), and 422 for every other BadRequest. The message says by how much, and that the application can raise the limit. BadRequest is defined in featherweight.errors, where streaming.py can import it; featherweight.adapters.errors still exports it.
    • A result: everything the provider says no to (a type the model cannot read, a file that is too large for it, too many pages). The turn ends FAILED with the provider's error, an error event is sent, and nothing is retried, as for any streaming agent.

    Files for agents and jobs¶

    Attachments are a feature of the chat. By design, an agent does not pass binary data to another agent, and a job does not carry it: not to a launched agent, not to a background job, not to an agent wrapped in a job (as_job), and an agent that a pipeline runs has no field that takes a file either. Their input is JSON that a model or a queue carries. A model cannot write bytes; a queue message, the job store, the input hash and the traces would all carry them; and the run log keeps no content. The other frameworks work the same way (checked 2026-11-25): Claude Code's sub-agents get only the prompt string, Pydantic AI's delegation passes text and shared dependencies, OpenAI's Agent.as_tool takes text or structured parameters, and Google ADK and LangChain Deep Agents share named files that are loaded on demand. So there is no attachments field on AgentInput and no argument of the runner for it, and none is planned.

    What to do instead: pass references. Keep the file in a store that you manage (a database, a disk, S3) and put its reference, an id or a name, in the input of the job or the agent. A tool fetches it:

    • The input says what to work on, the identity says who may read it (identity), and the tool does both the fetch and the check. The model sees the reference, and may pass another one: the tool checks that the identity may read the one it was given.
    • The tool returns the text of the file, which every provider takes, or an image or a file block, which reaches the model as it is and is read where the provider accepts it (what was verified).
    • A pipeline that downloads a file stores it, and passes the reference on to the agent. That is one more step, for a case that is rare.
    • A resume reuses a step for the same input and the same identity, so for the same reference, even if the file behind it changed (resuming). Put a version or a hash in the reference when that matters.

    A recipe shows it, with a test.

    Decisions¶

    • Attachments are for a chat; agents and jobs pass references. A file does not travel between agents, or through a queue. See above.
    • Transport only. No capability checks, no conversion, no fetching, no uploads. The application knows its model and its users.
    • data only. Safe by construction, and the one source that every provider's package accepts.
    • One form of base64, and an error that says which mistake. Strict and predictable: what b64encode and btoa give. A lenient reader (taking a data: prefix, line breaks, the URL-safe alphabet) would guess, and the size of an attachment is counted from its length. The error says what the likely mistake is, so the developer does not have to find out.
    • An empty attachment is refused, as a wrong input is raised and not left to fail in the run.
    • Validate without a decoded copy. The input is built before the agent's limits are known, so it cannot refuse a conversation that is too large first; what it can do is not to hold a second copy of every attachment while it checks.
    • All four media types. They map in the same way, so supporting two and refusing two would add code and not remove any.
    • Limits are on the agent, with cautious defaults that all three big providers accept, so that most applications need no setting.
    • The run log keeps no content. It holds no message text today, and holds no attachment now: not the bytes, not the name.

    Not supported¶

    • Fetching URLs, uploading to a provider's store, and file_id sources: the application's.
    • Converting a PDF into page images, resizing, transcribing or OCR, for a model that cannot read the original.
    • Checking that a model can read a type, or the provider's own limits (pages, pixels, duration).
    • Attachments on an assistant or tool message, and in the input of an agent or a job: a launched agent, a background job, an agent wrapped in a job, or one that a pipeline runs. They pass references (above).
    • Stored attachments. The application keeps them, as it keeps the conversation.

    Findings¶

    Checked while writing this (2026-11-22):

    • ag-ui-protocol 1.0.0: ContentPart is text, image, audio, video or document; a source is data (value, mime_type required) or url; there is no source for a provider's file id. BinaryInputContent is kept only for importing.
    • langchain-core 1.8.3 has standard blocks image, audio, video, file and text-plain, each with base64, url, file_id and mime_type. The three provider packages here translate them.
    • Anthropic (langchain-anthropic 1.7.11): base64 and URL for images and documents, and file_id.
    • Google (langchain-google-genai 4.4.2): base64 for all types; gs://, YouTube and Google-hosted URLs go through; any other http(s) URL is downloaded by our process and inlined.
    • OpenAI (langchain-openai 1.8.2): base64 images; PDFs inline as file_data, on Chat Completions (PDF only) and Responses (more types); audio inline; file_url for files on Responses only; file_id.
    • Ollama takes images only, as base64 in an images array, on vision models; no PDFs. featherweight has no Ollama provider, and langchain-ollama was not checked: an application that adds one (see models) finds out which blocks it accepts.
    • What the LangChain packages do with our blocks (checked offline, nothing sent, tests): Anthropic sends images and PDFs as base64 blocks and raises for audio and video while it builds the request; OpenAI Chat Completions sends images, PDFs (a LC_AUTOGENERATED name and a warning without a filename) and audio, and raises for video; OpenAI Responses sends images and files, raises for video, and drops audio without any error, so the model sees only the text; Google sends every block inline. Only OpenAI gets the filename. A text file passes through Anthropic and Chat Completions, although Chat Completions takes only PDFs. This is the packages' behaviour on the dates above and it changes: the tests describe the versions of uv.lock, the floors in pyproject.toml let an application install others, and a test of the Google package that fails after an upgrade says that the package changed (its private function is imported inside the helper, so only those tests fail).
    • Observers: an observer that captures content (capture_content=True, and OpenTelemetry with content capture on) is given the attachment bytes with the rest of the messages. That is the documented opt-in. By default no event, run log row, observer record or span holds any of it.
    • What a provider returns or logs is the provider's: featherweight puts no attachment bytes in an event or a log line, and guarantees nothing about what a provider's endpoint puts in its error text or keeps in its own logs. The text of a failure is passed on as it is, to the client (RUN_ERROR) and to the application's log; the run log keeps only the error's type and a hash of its text.
    • A file returned by a tool (2026-11-25, real calls, the smallest model of each provider, one small file each: a 200 px JPEG and a one-page PDF). A tool that returns [text block, image or file block] reaches the model as a list of content blocks, unchanged, and the model read both files with Anthropic (claude-haiku-5-5), Google (gemini-3.5-flash-lite) and OpenAI (gpt-6-luna, on the Responses API, the only one that featherweight's OpenAI settings build). Google's Gemma (gemma-4-26b-a4b-it) did not call the tool: it answers at once when an agent has a reply schema, so nothing is known for it. This is one run each, a snapshot and not a promise: text is the result that every provider takes, and media is for a provider that you have tried.
    • The body of a request carries each attachment as base64 inside the JSON, a third larger than the file, and every turn sends the whole conversation again. A server or a proxy in front of the application often has a lower limit on a body, and a body over it never reaches featherweight: the guide says so, and that max_bytes is the agent's policy and not the server's.
    • The Vercel adapter read only the text of a user message and dropped its file parts, so an attachment was lost. It now converts a file part with a data:...;base64, URL into an image, audio, video or document part by its mediaType, and refuses any other URL with a BadRequest. The AG-UI adapter needed no change.
    • What each provider accepts, with the limits, is in its own page: a dated snapshot, a suggestion and not a duty of a release. It says that it is not maintained and that the providers' pages are the source, and a developer checks them for the provider and the model that they use. It changes: Google raised its inline limit from 20 MB to 100 MB in January 2026, and its pages still disagree.

    Tests¶

    Never a real model, and no network.

    • The conversion: each part type to its block and back; the order of parts; filename; a message with only attachments.
    • Refusals: a url source, bad base64 (each of the mistakes of the table above, with its message), an empty attachment, a missing mime type, an unsupported part, a limit that is exceeded by count, by bytes, and by the attachments of earlier messages; the agent's own limits over the defaults.
    • The check agrees with Python's: over many generated strings, and at the edges of the chunks, it accepts what base64.b64decode(..., validate=True) accepts and refuses what it refuses (an empty value apart).
    • Memory: checking a large attachment does not allocate a decoded copy of it (the peak is measured).
    • The limit error: it is an AttachmentLimitError, a BadRequest and a ValueError; a limit of 0 refuses an attachment and passes text; a limit that is not a whole number of 0 or more is refused when the class is declared; over HTTP, a handler answers the limit error with 413 and its message, and a malformed body with 422.
    • The provider's side, offline: build the request that each of the three packages would send for each block, and check its shape without sending it.
    • A fake model that fails on a block: the run is FAILED, the error event is sent, and there is no retry.
