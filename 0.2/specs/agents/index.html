    Agents¶

    Status: implemented. How to use it is in agents.md. The code is models.py.

    Goal¶

    An agent is a static, typed definition. Pydantic is the specification: the input, the output, the tools, the skills, the sub-agents and the MCP servers are declared on the class and enforced by Pydantic, not by convention. A running agent is complete before it runs: nothing about it is decided while it runs, so it can be read, tested and versioned like any class, and its hash identifies it. The class can be written in code, or built from data (a file, a database row) when it is needed: the runner sees a class either way, and a definition built from data is checked as strictly as one written by hand. A malformed definition fails when it is built, before any model is called.

    The definition¶

    A subclass of AgentBase. The runner instantiates it (agent_cls()), so a subclass supplies defaults for every field.

    Field Type, default Rule
    name, description, version, prompt str, required name and version are recorded on every attempt. description is what a parent's model reads before it launches this agent
    model ModelSettings, Gemini() Which model runs the agent and how hard it thinks. A setting the model does not accept fails when the agent is built (models)
    tools list[BaseTool], empty Only these are bound to the model, besides the tools the runner adds (tools and the registry)
    recursion_limit int, 25, at least 1 Passed to langgraph. Stops a runaway tool loop inside one run; a run that hits it fails
    allow_user_questions, raise_conflicts bool, False Each only adds a sentence to the prompt. Neither is enforced
    subagents list[type], empty Agent classes this agent may launch (runner)
    background_jobs list[type], empty Agent or job classes this agent may start in the background (background jobs)
    skills list[Skill], empty Skills this agent can read (skills)
    mcp_servers list[StdioMCPServer \| HttpMCPServer], empty MCP servers whose tools this agent may use (MCP tools)
    input_model, output_model ClassVar, AgentInput and AgentOutput The agent's contract

    A subclass re-annotates a field it overrides (name: str = "x"), because Pydantic rejects an unannotated override.

    Checked when an agent is built¶

    Each of these raises a ValidationError (a programming error, not a failed run):

    • the output model: one that the agent's model cannot fill is refused by its model settings, which are in charge of everything that depends on the provider or the model (model settings). Claude is the example: some of its models take no dictionary.

    • subagents: every entry is an AgentBase subclass; none is the agent's own class; the names of the sub-agents are distinct.

    • background_jobs: every entry is a non-streaming agent class or a Job class; none is the agent's own class; the names are distinct; an agent may be in subagents too, to be run inline or in the background (the model chooses); an agent that is in a background_jobs list does not declare its own (background jobs).
    • skills: the names are distinct.
    • mcp_servers: the names are distinct. Each server model checks itself too (name format, timeouts, caps).
    • tools: the names are distinct, and none is launch_agent, get_agent_schema, get_skill, search_tools or call_tool, which the runner uses for its own tools.
    • model, recursion_limit: the allowed values above. model checks itself (models).

    Agent A listing B while B lists A is allowed. The runner's depth limit stops it.

    Input and output¶

    • AgentInput forbids extra fields (extra="forbid"). The runner raises TypeError for an input that is not an instance of the agent's input_model: a wrong type is a bug, so it raises. The input is sent to the model as indented JSON, in a single user message.
    • AgentOutput always carries open_questions: list[str], where a model reports a question or a conflict instead of guessing. It is never a failure. The task fields of an output should have defaults, so that a model that needs to ask is not forced to invent an answer to pass validation.
    • The output is enforced twice. The output model is the structured-output schema the model is given (response_format), and the reply is validated against it again. A reply that does not validate is a failed attempt.
    • check_output(agent_input, output) is the place for rules between the input and the output ("everything the model returned is in the input"). It raises ValueError to reject, which is a failed attempt and is retried. The default accepts everything. Rules about the output alone belong in validators on the output model.

    The system prompt¶

    Assembled by build_system_prompt(can_launch=True), in this order, and joined by blank lines:

    1. prompt
    2. one sentence for allow_user_questions, whichever way it is set, and one for raise_conflicts
    3. if the agent has subagents or background_jobs and can_launch: the agents it may start, each once, by name and description, in groups: the ones to launch inline, the ones to start in the background, and the ones that can be either (an agent in both lists), and how to use each tool. Their schemas are not in the prompt
    4. if the agent has skills: each skill's name and description, and how to read one
    5. if the agent has an MCP server with discover on (the default): the servers it can search, by name and description, and how to use search_tools and call_tool

    The runner sets can_launch to false for an agent at the depth limit. Its SHA-256 is recorded on every attempt (system_prompt_hash), so two runs can be compared by prompt. The discovery section is built from the declaration, so the hash is known before any server starts. Bound MCP tools add nothing to the prompt.

    The agent hash¶

    Every attempt also records agent_hash, the SHA-256 of the whole declaration, so that "this run used exactly this agent" can be checked. If system_prompt_hash is the same and agent_hash differs, the model, a tool or a limit changed, not the prompt. Resuming a job uses it: a run is reused only when the hash is the same (runner). The hash covers:

    • name, version, description, prompt, recursion_limit, allow_user_questions, raise_conflicts
    • the model settings, all fields
    • each tool's name, description and argument schema, as the model sees them
    • each sub-agent's own declaration, recursively. A sub-agent already being described further up is named only, so a cycle ends
    • each agent in background_jobs the same way (a job class by its name, version and job_hash), only when there are some, so that an agent without any keeps the hash it had
    • each skill in full, and each MCP server as declared (environment variable names, never values)
    • the assembled system prompt
    • the JSON schema of the input_model and of the output_model, so that a changed field, type, description or default is another agent (check_output is code and is not hashed: version is its signal, and a reused output is checked against it again)

    The declaration is built as a plain structure, written as JSON with sorted keys and fixed separators, and hashed, so equal declarations give the same hash in any process. The code inside tools and in check_output is not covered: version is the signal for that. Rows from before the column existed have NULL.

    Decisions¶

    • Static, and classes, not instances. A definition has no per-run state. A run passes the class and the input, and the runner builds the agent. A different prompt is a different class, with a new version. Static means complete before the run, not written in the source: an application may build the class from data, when a request arrives, with its own rules about what a user may choose. What the runner needs is a validated class, and its hash says which agent ran. How the class is made is the application's.
    • Who runs an agent is not part of it. An identity is an argument of the run, so the same agent runs for every user, and it is not in agent_hash (identity).
    • The instruction flags are not enforced. allow_user_questions and raise_conflicts only tell the model what it may do. An output that asks a question when asking is forbidden is not rejected.
    • A failing rule is the pipeline's, not the agent's. check_output only rejects. It cannot fix the output or decide what a failure means: the pipeline does.
    • Flat output schemas for Gemini. A nested or nullable structured-output schema can come back silently truncated (a tree with only its root). Prefer flat lists with ids, avoid X | None on nested objects, and add a check_output that compares the output with the input. The example pipeline builds its trees from flat lists for this reason.
    • The model is typed, one class per provider. A typo, or an effort a model does not accept, fails at build time. Other models and providers are a subclass (models).

    Not supported¶

    • Per-run overrides of the prompt, model or tools.
    • Models other than the three Gemini models, and provider-specific settings (a thinking budget).
    • Enforcing allow_user_questions and raise_conflicts.
    • Output validation that feeds the error back to the model. A retry resamples with the same input (runner).
    • Streaming from an ordinary agent. A streaming agent is a subclass (StreamingAgent) with its own input, no output model and no retries.

    Tests¶

    test_models.py covers the defaults, that declarations are frozen, the prompt flags and the prompt hash, that a class built from data (create_model) is refused for the same malformed definitions as one written with class, with the same message, and test_model_settings.py the models and efforts each provider class accepts; test_runner.py covers input type errors, output validation and check_output; the build-time checks are in test_subagents.py (sub-agents), test_skills.py (skills), test_mcp.py (servers and the reserved tool names) and test_registry.py (duplicate tools).
